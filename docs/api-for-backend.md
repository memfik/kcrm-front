# kCRM — что нужно от API (для бэкенда)

Документ для разработчика бэкенда. Фронт (этот репозиторий) готов на демо-данных: все 47 макетов перенесены, данные берутся из `src/data/*-demo.json` и генерируются в конфигах. Здесь — что каждой странице нужно от API, чтобы подключить реальные данные. Эндпоинты и формы ответов — **предложение**: названия и детали можно менять, главное — состав данных и действий. Когда API будет готово, фронт подключим к нему (см. «Как фронт подключится»).

Связанные документы: `docs/backlog.md` — что на каждой странице заглушка и чем отличается от макета; `docs/design-handoff.md` — описание дизайна; `src/config/nav.ts` — все разделы (номер = номер макета).

## Как устроен фронт (где смотреть)

- **Почти все страницы — списки по одному шаблону.** Раздел описан конфигом `src/config/lists/<файл>.tsx`: тип записи, вкладки (`tabs`), фильтры (`filters`), колонки (`cols`), KPI (`kpis`), карточка записи (`record`: вкладки, действия), форма. Смысл каждого поля конфига — `src/lib/list/types.ts`. Маршруты: `/<key>` — список, `/<key>/<id>` — карточка; создание и правка — панель справа (`/<key>/new`, `/<key>/<id>/edit`).
- **Форма записи** строится по колонкам списка (`src/lib/list/auto-form.ts`, `formOf`): поля в порядке колонок, первое обязательно; часть полей записи в форму не попадает — им бэкенд ставит значения по умолчанию. Единственная проверка на фронте — обязательное первое поле, **валидация — на бэкенде**.
- **Отдельные страницы** (не шаблон): вход `/login` (01), главная `/` (02), конструктор КП `/offer-builder` (28), профиль `/profile` (29), конструктор договора `/contract-builder` (30), свод по продажам `/sales-summary` (31).
- **Сквозные идентификаторы:** `cs` — id контрагента (число, 0 — не указан); `u`, `uid`, `ex`, `mgr` — uid сотрудника (строка, тот же, что в `GET /me`); `deal` — id сделки; № КП = id запроса скидки. Даты — `YYYY-MM-DD`, дата-время — `YYYY-MM-DD HH:MM` (лучше ISO 8601), деньги — число в тенге.
- **Демо «сегодня»** — 30.03.2018 (последний день копии базы), опорный месяц периодов — `2018-03`. С API периоды считаются от текущей даты.

## Общий контракт

База — `/api/v1`. Ключ раздела `<key>` = `key` в конфиге = путь страницы (`deals`, `tech-requests`, `job-orders`…). В разделах ниже повторяется только то, что отличается от этого контракта.

**Список**
```
GET /api/v1/<key>?q=&tab=&<filterKey>=a,b&owner=<uid>,<uid>&sort=<col>|-<col>&page=1&per=20&from=&to=
→ { items: T[], total: number, tabs: { [tabKey]: number } }
```
- `q` — поиск (поля перечислены в разделе), `tab` — ключ вкладки, фильтры — ключи `filters[].k`, `owner` — колонка ответственного, `sort` — ключ колонки (минус — по убыванию), `from`/`to` — диапазон по колонке-дате («Ещё» в списке).
- `tabs` — счётчики на вкладках (с учётом поиска и фильтров, без учёта самой вкладки).
- Сейчас фронт фильтрует, сортирует и листает сам (страница 20 строк). Для больших разделов это переедет на сервер — поэтому параметры нужны сразу.

**Запись и изменения**
```
GET    /api/v1/<key>/:id              → T (+ данные вкладок карточки, если в разделе не указаны отдельные эндпоинты)
POST   /api/v1/<key>                  → T   (создание; тело — поля формы; номер записи генерирует бэкенд)
PATCH  /api/v1/<key>/:id              → T   (правка; в финальных статусах — 409)
DELETE /api/v1/<key>/:id
POST   /api/v1/<key>/bulk-delete { ids }
POST   /api/v1/<key>/:id/assign { uid, comment }     — «Передать»/«Делегировать» (и bulk: { ids, uid, comment })
POST   /api/v1/<key>/:id/<action> { ... }  → T       — решения и смены статуса из карточки (перечислены в разделах)
```
Удаление в сделках — не удаление, а «Расторгнуть» с датой и причиной (см. 04).

**Сводки и выгрузки**
```
GET  /api/v1/<key>/kpis?period=m|q|y&anchor=YYYY-MM   → [{ key, value, prev? }]   — карточки KPI; prev — за прошлый период
GET  /api/v1/<key>/series?metric=&months=12&anchor=   → { "YYYY-MM": number }      — график «По месяцам» (+ год назад)
GET  /api/v1/<key>/export?<параметры списка>          → xlsx (сейчас фронт выгружает CSV сам)
POST /api/v1/<key>/import (multipart)                  — где есть «Импорт»
```
После любых изменений KPI должны быть актуальны: сейчас на фронте они считаются по демо-массиву и после правок не пересчитываются — с API фронт будет брать их из `/kpis`.

**Справочники и пользователь**
```
GET /api/v1/dict/<name>   — сотрудники, филиалы, подразделения, технологии, услуги, виды работ, причины расторжения…
GET /api/v1/me            → { uid, login, name, initials, department, roles: string[], blocks: string[] }
```

## Вход, права, безопасность

- Вход через AD/SSO (`POST /auth/login` или SSO-редирект, сессия в HttpOnly cookie) — подробно в 01. **Пароль никогда не логировать** (тело `/auth/login` исключить из логов, трассировки, APM), лимит попыток.
- Права: роль, подразделение и видимые блоки — из AD (`/me`, матрица прав — 45). Фронт сейчас права не проверяет, **всё проверяет бэкенд**: доступ к спискам и вкладкам (например, 38 «Мои / Отдела / Все»), допустимые направления делегирования (45), правку в финальных статусах (409).
- Значения, которые считаются (сроки, суммы, остатки, статусы по датам, номера), бэкенд считает сам и не принимает от клиента.

## Интеграции и фоновые задачи (сводка)

Подробности — в «Общих наблюдениях» каждой части.
- **Интеграции:** AD/SSO; Oktell (журнал звонков, записи, звонок по клику); биллинг (начисления, тест без начислений, доплата за временное увеличение); ЕСТУ (ID-каналы, IP, нумерация, карта сети и узлы); LD / СЭДО (договоры, сканы актов, подписание); геокодеры 2ГИС / Яндекс / Google; портал госзакупок (тендеры); e-mail; файловое хранилище (вложения, шаблоны, записи, печатные формы); генерация PDF / DOCX / XLSX на сервере.
- **Фоновые задачи:** синхронизация Oktell и AD; ежедневный пересчёт статусов по датам (просроченные задачи, тесты 41, увеличения 42); напоминания за 5 дней до окончания (41, 42); автоотключение теста и автовозврат объёма к договору; автоматика при наряде на отключение (изъятие IP, нумерация, заявка на смену статуса ID-канала); сверка с ЕСТУ; рассылка отчётов «По расписанию» (общий `report-schedules`).

## Как фронт подключится (для понимания)

- Все записи разделов фронт читает через одно хранилище `src/lib/list/store.ts` (`useRows`, `rowsStore`) — его заменим на загрузку из API с кешем; конфиги вместо `rows()` получат источник `list / get / save / remove`. Поэтому важно, чтобы формы ответов были **одинаковыми для всех разделов** (общий контракт выше).
- Карточка будет загружать запись по id (`GET /<key>/:id`), а не искать её в загруженном списке.
- Новая запись будет начинаться с заготовки по умолчанию (поля без колонки в форме) — удобно, если бэкенд отдаёт её: `GET /api/v1/<key>/new` → T (необязательно).

### 01 Вход — `/login`
- **Сущность** — сессия пользователя. Сейчас пользователь — константа `CURRENT_USER` (`src/lib/current-user.ts`):
  `{ initials: string, name: string — ФИО, login: string — логин AD, department: string — подразделение }`. Используется в шапке, профиле, мобильном меню, приветствии на главной и в авторе сообщений чата.
- **Форма** (`src/components/login/login-form.tsx`): `login` (обязательно, autocomplete=username), `password` (обязательно), `remember: boolean` («Запомнить меня», по умолчанию true). Подпись: «логин и пароль от домена JusanMobile».
- **Эндпоинты**
  - `POST /api/v1/auth/login { login, password, remember }` → `200` + сессионная cookie (HttpOnly, Secure, SameSite=Lax; при `remember=false` — сессионная, без Max-Age) + тело `GET /api/v1/me`. Ошибки: `401 { error: "invalid_credentials" }`, `423 { error: "locked" }` (блокировка в AD), `503` — AD недоступен.
  - Альтернатива или дополнение: SSO (Kerberos/SAML/OIDC) — `GET /api/v1/auth/sso` → редирект к IdP → `GET /api/v1/auth/callback`.
  - `POST /api/v1/auth/logout` — завершить сеанс. Сейчас «Выйти» — просто ссылка на `/login`.
  - `GET /api/v1/me` → `{ uid, login, name, initials, department, roles: string[], blocks: string[], photo?: string }`. `uid` — тот же ID сотрудника, что в колонках `u`/`uid`/`ex`/`mgr` всех разделов.
- **Безопасность (§7)**: пароль не писать в логи, трассировку и APM, тело запроса `/auth/login` исключить из логирования; ограничение частоты попыток по логину и IP; только HTTPS.
- **Плитки слева** (`login-tiles.tsx`): «Вход звонком», «Вход по документу», «План продаж 72%» — декоративные, локальное состояние. API не нужно, пока не решено вводить альтернативные способы входа.
- **Подвал «Служба работает»** — статичный текст. При желании: `GET /api/v1/health` → `{ ok: boolean }`.
- **Сейчас на фронте**: отправка формы без проверки сразу ведёт на `/`; сессии нет.

### 02 Главная — `/`
Дашборд со сравнением периодов (переключатель м/кв/год, опорный месяц `2018-03`). Предлагаю один агрегирующий эндпоинт:
`GET /api/v1/home?period=m|q|y&anchor=YYYY-MM` →
```ts
{
  offers:    { [ym: string]: { n: number; sum: number } } // КП по месяцам (кол-во, сумма ₸); demo offers[i] = [ym, n, sum]
  contracts: { [ym: string]: number }                     // подписанные договоры; demo contracts[i] = [ym, n]
  activity:  { [ym: string]: number }                     // события ленты; demo activity[i] = [ym, n]
  accounts:  { status: 0..6; count: number }[]            // лицевые счета по статусу биллинга; demo curstat[i] = [status, count]
  managers:  { uid: string; count: number; prev: number }[] // топ-10 по числу КП за период и прошлый; demo mgr[i] = [uid, ym, n]
  recentOffers: { id; cs; u; date; sum; act }[]           // 10 последних КП; demo recent[i] = [id, cs, uid, date, sum, act]
  feed: { id; cs; u; date; kind: string }[]               // 6 последних сделок/обращений; demo deals[i] = [id, cs, uid, date, kind, …4 не используются]
}
```
- Ряды по месяцам — минимум 24 месяца до `anchor`: графики КП и договоров показывают последние 12 месяцев плюс пунктир «год назад».
- **KPI** (за период и прошлый период): «КП выставлено» — число КП; «Сумма КП» — сумма ₸; «Новые договоры» — подписано договоров; «Активность в ленте» — число событий. В подзаголовке «Коммерческие предложения» — сравнение с тем же периодом год назад.
- **Статусы лицевых счетов** (общий справочник `dict/account-status`, совпадает со статусом контрагента): 0 Не определён, 1 Перспективный, 2 Есть интерес, 3 Активный, 4 Неактивный, 5 Приостановлен, 6 Отказ.
- **Статус КП в «Последних КП»**: `act=1` → «Согласовано», иначе при `sum>0` → «На согласовании», иначе «Черновик» (как в разделе 05).
- **Лента**: `kind` содержит «обращ» → иконка обращения; ссылка ведёт на `/deals/:id`.
- Приветствие: `me.name`. Время — по Астане (`Asia/Almaty`), считает клиент.
- Быстрые ссылки — статичные, API не нужно.
- **Сейчас на фронте**: все цифры из `src/data/home-demo.json`; названия компаний и ФИО — заглушки по ID.

### 03 Контрагенты — `/counterparties`
- **Сущность** `Counterparty`:
  `id: number` — ID контрагента (= `cs` в остальных разделах); `uid: string` — владелец (менеджер); `name`; `form` — ЮЛ форма собственности (ТОО/АО…); `bin` — БИН/ИИН; `seg` — сегмент (B2B, B2G, B2C, B2O, КМГ); `ind` — потребительский сегмент (отрасль, 8 значений); `cat: 0..4` — категория (Потенциальный, Периодический, Постоянный, VIP, TOP 500); `typ` — тип клиента (Корпоративные клиенты, SMB, Партнеры, Операторы связи, Физические лица); `st: 0..6` — статус (как у лицевых счетов в 02); `kp` — число КП; `ct` — число договоров; `dl` — число сделок; `cc` — число контактов; `last: string|null` — дата последнего КП; `city`.
  Demo: `counterparties-demo.json[i] = [id, uid, kp, last("NULL"), ct, dl, st, cc]`. Остальные поля в демо — заглушки по ID.
  `kp`, `ct`, `dl`, `cc`, `last` — вычисляемые счётчики: их отдаёт сервер, а не правит пользователь.
- **Список**: поиск `q` по `name`, `bin`, `id`. Вкладки: `all`; `my` → `uid = me.uid`; `other` → `uid ≠ me.uid`; `ct` → `ct > 0`. Фильтры: `st` (0–6), `seg`, `cat` (0–4), `typ`. Сортировка по умолчанию `-last`; диапазон дат — по `last`. Колонка ответственного `owner` = `uid` («Владелец»).
- **KPI**: «Всего в работе» — число контрагентов с КП или договором (без prev; в примечании — общее число, «из 7 683»); «Получили КП» — контрагенты, у которых `last` попадает в период (есть prev); «КП выставлено» — число КП за период (prev); «С договорами» — `ct>0` и доля от «в работе» (без prev).
- **Карточка** — `GET /api/v1/counterparties/:id`. Вкладки:
  - «Информация» — поля записи + `source` («Источник обращения»: Гос. закупки / Холодный звонок / Сайт / Рекомендация — в типе такого поля нет, нужно добавить).
  - «Контакты» — `GET /api/v1/counterparties/:id/contacts` → `{ id, name, position, phone }[]`; кнопка «Позвонить» — ссылка `tel:`.
  - «Местоположение» — точка подключения `{ city, address, lat?, lng?, isConnectionPoint: bool, invoiceDelivery: bool }` (карта OSM).
  - «Связанные IP-ресурсы» (новое, ОТУП ДИППП) — `GET /api/v1/ip-requests?cs=:id` → `{ id, act, address, st }[]` (заявки раздела 11 по точкам клиента).
  - «Реквизиты» — `{ bank, iik, kbe }`.
  - «Доступ» — `GET /api/v1/counterparties/:id/access` → `{ uid, department, level: "full"|"read" }[]`.
  - «История» — `GET /api/v1/counterparties/:id/history` → `{ t, p, d }[]` (журнал действий).
- **Действия**: «Составить КП» → `/offer-builder?cs=`; «Новая сделка» → форма сделки с `cs`; «Заявка на ТВ и ТР» → форма 09 с `cs`; «Событие» → `/calendar` (в макете — диалог создания события: `POST /api/v1/calendar { cs, … }`). «Передать» — `assign` (меняет `uid`). Удаление — стандартное. Кнопки шапки: «Новый контрагент», «Песочница» (ссылка), «Выгрузить в Excel» (export).
- **Форма** (по колонкам): `name`* (trim), `seg`, `cat`, `st`, `uid` (сотрудники); `kp`, `ct`, `last` в форме сейчас доступны для правки (автополя по колонкам) — на сервере принимать их только для чтения. Нужно добавить в форму `bin` (проверка: 12 цифр, уникальность), `form`, `typ`, `ind`, `city`. По умолчанию для новой записи: `uid = me`, `st = 0`, `seg = B2B`.
- **Справочники**: `dict/staff`, `dict/counterparty-status`, `dict/segments`, `dict/categories`, `dict/client-types`, `dict/industries`, `dict/cities`, `dict/legal-forms`.
- **Сейчас на фронте**: название, БИН, сегменты, реквизиты, контакты, IP-ресурсы и история — заглушки по ID. Вкладка «Мои» сравнивает с владельцем первой записи (`ME`). Импорта и массового «Делегировать» нет.

### 04 Сделки — `/deals`
- **Сущность** `Deal`:
  `id`; `pid: number` — родительская сделка (≠0 — доп. соглашение); `date` — создана; `cs` — контрагент; `u` — менеджер; `name`; `serv` — услуга; `exp` — ожидаемая сумма ₸; `fore` — прогноз ₸; `fact` — факт ₸; `fin: 0|1` — завершена; `succ: 0|1` — успешно; `canc: number` — причина расторжения (0 — не расторгнута); `cancDate?` — дата расторжения; `stg: string` — этап (ID из справочника); `acts: number` — число действий.
  Demo: `deals-demo.json.deals[i] = [id, pid, date, cs, u, name, exp, fore, fact, fin, succ, canc, stg("NULL"→"0"), acts]`; `serv` в демо — заглушка.
  Справочники в том же файле: `stages[i] = [id, code, text, pct, color]` (11 этапов: 0 НЕТ, 1 Т1 Первичные переговоры 0%, 2 В1 10%, 3 ПОТР 20%, 4 ТР 30%, 5 КП 40%, 6 В2 50%, 7 ДОГ 70%, 8 ПОДКЛ 100%, 9 ЗАВЕРШЕНИЕ 100%, 10 ВЫХОД — аннулирована); `cancel[i] = [id, text]` — 30 причин расторжения (`deal_cancel_list`).
- **Список**: поиск по `name`, имени контрагента, `id`, `serv`. Вкладки: `w` → `!fin && !canc`; `d` → `fin && succ`; `c` → `canc || (fin && !succ)`; `a`. Фильтры: `stg`, `u`. Сортировка `-date`; диапазон по `date`. Ответственный — `u` («Менеджер»). Сортировка по `stg` идёт по `pct` этапа.
- **KPI**: «Новые сделки» — создано за период (prev); «Ожидаемая сумма» — Σ`exp` созданных за период (prev); «В работе» — `!fin && !canc` сейчас; «Конверсия в договор» — % сделок с этапом `pct ≥ 70`. Опорный месяц у сделок свой (в демо `2017-08`, с API — текущий).
- **Аналитика «Воронка»**: `GET /api/v1/deals/funnel` → `{ [stageId]: count }` — число сделок на каждом этапе сейчас.
- **Карточка**, вкладки:
  - «Этапы» — путь по этапам 1–9 и баннер расторжения (причина + дата); «Действия» — `GET /api/v1/deals/:id/actions` → `{ t, p, d }[]`.

### 06 Запросы скидки — `/discount-requests`
- **Сущность** `Discount` (запрос на согласование скидки в КП; ключ записи — № КП):

- **Карточка**:
  - «Позиции» — `GET /api/v1/discount-requests/:id/items` → `{ name, price, disc: %, allowed: % }[]` (запрошенная и допустимая скидка; превышение подсвечивается) + `comment` (обоснование менеджера).
  - «Маршрут» — цепочка согласования `{ step, uid, decision?, d }[]` (первый и второй согласующий).
- **Действия** (видит согласующий с флагом `coapp`):
  - «Подтвердить» → `POST /api/v1/discount-requests/:id/approve` → `state=ok`;
  - «Частично» → `POST …/:id/partial { items: [{ itemId, approved: bool, disc? }] }` → `state=part`, `ok` = число одобренных;
  - «Отклонить» → `POST …/:id/reject { comment }` → `state=rej`.
  Решение должно обновлять КП (05: `act`, согласованная стоимость). Шапка: «Согласовать выбранные» → `POST /api/v1/discount-requests/bulk-approve { ids }` (на фронте есть отмена — нужен откат или подтверждение); «Выгрузить».
- **Форма**: `id` (№ КП, только чтение — запрос создаётся из КП), `cs`* (ID), `u`, `date` (пусто → сегодня), `s`, `es`, `state`. Правильнее создавать запрос как `POST { kp, items:[{itemId, disc}], comment }`, а `cs`, `s`, `es` брать из КП.
- **Справочники**: `dict/staff`, лимиты допустимой скидки (`dict/discount-limits`, сейчас константа 10%).
- **Сейчас на фронте**: решение — заглушка по ID, позиции и маршрут сгенерированы; `?kp=` из КП не подставляется.

  - «Услуги» — ежемесячные услуги `{ name, qty, start }[]` и технические параметры `{ bandwidth, subnet, cpe, cross }`.

### 11 Заявки IP — `/ip-requests`
- **Сущность** `IpRequest`:
  `id` (отображается как «IP-700»); `cs`; `deal`; `u` — инициатор; `act` — требуемое действие (Выдача / Изъятие / Переоформление / Изменение); `block` — размер блока, адресов (4/8/16/32/64; префикс = 32 − log2(block)); `tech` — последняя миля (ВОЛС, РРЛ, Радиомост, Спутник, БШД); `speed` — Мбит/с; `br` — филиал; `date`; `st: "dr"|"rv"|"w"|"p"|"d"|"r"|"o"` — Черновик / На рассмотрении / В ожидании / В процессе / Готово / Отклонено / Отозвано; `auto: boolean` — создана автоматически по наряду на отключение.
  Демо JSON нет: 120 заявок собраны из строк заявок ТВ/ТР (`cs=t[3]`, `deal=t[4]`, `u=t[5]`).
  Добавить: `connType` (Новое / Дополнительное / Тестовое), `addrType` (Публичный), `contract`, `workOrderId` (для `auto`), `sourceRequestId` (исходная заявка на выделение), ответ исполнителя `result: { subnet: "185.x.x.0/29", gateway }`.
- **Финальные статусы** `d`, `r`, `o`: запись заблокирована (`locked`) — сервер должен отклонять `PATCH` (`409`), действия в карточке скрыты.
- **Список**: поиск по имени контрагента, `deal`, ФИО инициатора. Вкладки: `w` → `st ∈ {w,p,dr,rv}`; `d` → `d`; `r` → `r|o`; `a`. Фильтры: `act`, `tech`. Сортировка `-date`; диапазон по `date`. Ответственный — `u` («Инициатор»; только фильтр, без «Передать»).
- **KPI**: «Заявок» — за период (prev; сейчас условный ×0.9); «Выдано адресов» — Σ`block` у `st=d && act=Выдача`; «В ожидании» — `st=w`; «Отклонено» — `st=r`.
- **Карточка**:
  - «Заявка» — баннеры «Финальный статус» и «Создана автоматически (по наряду Н-…, из заявки IP-…)»; параметры «подтянуты из базы» (договор, тип подключения, миля, скорость, блок, тип адреса, филиал).
  - «Ответ» — ответ исполнителя (блок, шлюз) при `st=d`; синхронизация с **ЕСТУ «IP-адреса»**: `{ synced: bool, at? }`.
  - «Уведомления» — журнал писем `GET /api/v1/ip-requests/:id/mails` → `{ to, what, d }[]` (создана, на рассмотрении, исполнена / IP изъят).
  - «Связанные» — другие IP-заявки клиента: `GET /api/v1/ip-requests?cs=`.
- **Действия** (только в нефинальном статусе):
  - «В работу» → `p`;
  - «Готово» `done { subnet, gateway }` → `d`, синхронизировать с ЕСТУ и отправить письмо инициатору;
  - «Отклонить» `reject { comment }` → `r`;
  - «Отозвать заявку» `recall` → `o`; только из `dr`/`rv`, иначе `409`; письмо исполнителю.
  Статусы `rv` и `w` действием не выставляются — нужен переход «Отправить на рассмотрение» (`dr→rv`; сейчас через форму) и, у исполнителя, `rv→w`. Шапка: «Новая заявка», «Отчёт по IP» (`/ip-report`), «Выгрузить».
- **Форма**: `id` (только чтение), `cs`* (ID; `date` = сегодня), `deal`, `tech`, `u`, `br`, `date`, `st` (только `dr`/`rv`; из других статусов форма статус не меняет). Полей `act`, `block`, `speed` в форме **нет** — их нужно добавить (обязательные).
- **Справочники**: `dict/ip-actions`, `dict/last-mile`, `dict/branches`, `dict/staff`.
- **Сейчас на фронте**: все 120 заявок — пример данных; письма, ЕСТУ и авто-изъятие — заглушки; ответ исполнителя сгенерирован.

### 13 Абоненты — `/subscribers`
- **Сущность** `Subscriber` (заявка в очередь абонентского отдела на заведение клиента в биллинг):

- **Карточка**: одна вкладка «Абонент» (ссылки на контрагента и сделку, даты, комментарий).
- **Действия** (пока нет `fin`): «Завести в биллинг» `enter` → `stw||=сегодня, fin=сегодня, succ=1` — **интеграция с биллингом**: создать лицевой счёт и вернуть его номер (`account`); «Отклонить» `reject { comment }` → `fin=сегодня, succ=0`. Шапка: «Взять в работу» → `POST /api/v1/subscribers/bulk-take { ids }` (только новые: `stw=сегодня`, `u=me`), «Выгрузить».
- **Форма**: `deal`* (№ сделки; `cs` сервер берёт из сделки — в форме его нет), `u`, `stw`, `fin`, `cm`, `succ` (автовыбор). Заявку в абонотдел логичнее создавать автоматически на этапе сделки «ПОДКЛ».
- **Справочники**: `dict/staff` (абонотдел).

### Общие наблюдения (01–14)

> Форма собирается по колонкам списка (`formOf` в `src/lib/list/auto-form.ts`): поля идут в порядке колонок без `noSort`, первое поле обязательное; если у раздела есть свои `fields`, они подставляются по ключу колонки; колонки, которых нет в записи, показываются только для чтения; полей, у которых нет колонки, в форме нет — их значения берутся из `blank`. Единственная проверка на фронте — обязательность первого поля, остальное должен проверять сервер.
> `u`, `ex`, `mgr` — uid сотрудника (строка), `cs` — id контрагента (число, 0 — не указан).

### 15 Задачи — `/tasks`
- **Сущность** `Task`: `id: number`; `cs: number` — клиент (0 — внутренняя); `date: string` — срок «YYYY-MM-DD HH:MM»; `d: string` — тема; `u: uid` — кто поручил; `ex: uid` — исполнитель; `st: "new"|"work"|"done"|"late"` — Не начато / В работе / Исполнено / Срок истёк. Плюс **тип** `ty: "На ознакомление"|"К исполнению"|"Срочное исполнение"`: сейчас вычисляется как `id % 3`, его надо хранить.
  Демо `tasks-demo.json`: `tasks: [id, cs, date, d, u, ex, ?, ?][]` (ex = "0" → исполнитель = u; индексы 6–7 не используются); `byMonth: [YYYY-MM, count][]`.
  `late` должен выставлять сервер, когда срок прошёл, а задача не исполнена.
- **Список**: вкладки `w` Актуальные (new|work), `l` Просроченные, `d` Исполненные, `a` Все. Фильтр `ty`. Поиск `q`: тема, имя клиента, ФИО исполнителя. Сортировка по умолчанию `-date`. Колонка ответственного — `ex`. Диапазон дат — по `date`.
- **KPI**: «Задач и событий» — число за период + `prev` (из series); «Актуальные» — new+work сейчас; «Просрочено»; «Исполнено вовремя, %» = done / (done + late). `series?metric=count` — задачи и события по месяцам.
- **Карточка**: вкладки «Задача» (параметры) и «Чат». Чат сейчас статичный → `GET /tasks/:id/messages` → `[{ t, p: uid|ФИО, d: datetime }]`, `POST /tasks/:id/messages { text }`. Первые записи чата («Задача поставлена», «Принято в работу») — события журнала.
- **Действия**: «Исполнено» (если не done) → `POST /tasks/:id/done` → `st=done`. «Отложить» → `POST /tasks/:id/postpone { date, remind_at? }`: сейчас срок просто сдвигается на +1 день, а `late` меняется на `work`; в макете — диалог с датой и напоминанием. «Переназначить» → стандартный `assign` (меняет `ex`).
- **Форма**: тема `d` (обязательно), поручил `u`, клиент `cs` (вводится по ID), срок `date` (дата; время сохраняется старое или по умолчанию 18:00; пусто → сегодня 18:00), исполнитель `ex`, статус `st` (выбор из встречающихся кодов). Тип в форме не задаётся — нужно добавить поле.
- **Справочники**: сотрудники (`dict/staff`), контрагенты (поиск).
- **Сейчас на фронте**: 600 задач из копии базы; статус и тип — заглушки; чат хранится только в памяти; бейдж «4» в меню и «Мои задачи: 4» не связаны с данными → нужен `GET /tasks/count?owner=me&tab=w`.

### 16 Календарь — `/calendar`
- **Сущность** `CalendarEvent`: `id`; `cs: number` — клиент (0 — внутреннее событие); `date: "YYYY-MM-DD HH:MM"`; `d: string` — описание; `u: uid` — автор; `done: boolean`. Источник — те же строки `tasks-demo.json` за март–апрель 2018, то есть события и задачи сейчас в одной таблице. Нужно решить: это одна сущность с типом (задача/событие) или две. Напоминания (`remind_at`) как сущности пока нет.
- **Список**: открывается сначала вид «Календарь» (сетка месяца), второй вид — таблица. Вкладки сейчас жёстко заданы месяцами («Март 2018», «Апрель 2018», «Все») — с API нужен диапазон `from/to` по `date`. Поиск: описание и клиент. Сортировка `date` по возрастанию. Колонка ответственного — `u`, «Передать» нет. Карточек нет (`noCards`).
- **Сетка месяца**: `GET /calendar?from=YYYY-MM-01&to=YYYY-MM-31` — все события месяца без пагинации. «Перейти на сегодня» работает только на фронте (сегодня сейчас зафиксировано на 2018-03-15).
- **KPI**: «Событий в марте» (+prev — февраль), «В апреле» (запланировано), «Встреч с клиентами» (`cs != 0`), «Напоминаний» (сейчас 40% от числа событий, это заглушка). С API: события текущего и следующего месяца, события с клиентом, события с напоминанием.
- **Карточка**: одна вкладка «Событие». **Действия**: «Исполнено» → `POST /calendar/:id/done` (`done=true`); «Отложить на час» → `POST /calendar/:id/postpone { date }` (+1 час).
- **Форма**: когда `date` (дата, обязательно — первая колонка), событие `d`, автор `u`. Клиента `cs` в форме нет (нет колонки) — его надо добавить, как и время, длительность и напоминание. Клик по дню открывает новое событие, но дата не подставляется (нужен параметр предзаполнения).
- **Сейчас на фронте**: нет вида «Неделя»; «Исполнено» хранится только во вкладке.

### 17 План продаж — `/sales-plan`
- **Сущность** `PlanRow` — менеджер × год: `id = uid*10000 + год` (составной ключ; на сервере лучше натуральный ключ `(u, y)`); `u: uid`; `y: number`; `plan: number[12]` — план по месяцам, ₸; `fact: number[12]` — факт по месяцам, ₸ (только чтение, считает сервер).
  Демо `sales-plan-demo.json`: `[u, y, m(1–12), sum, ?][]` — одна строка на месяц (индекс 4 не используется). Факт сейчас — сумма КП менеджера за месяц (`offers-demo.json offers[i][2]=u, [4]=date, [7]=сумма`), а если КП нет — случайная оценка от плана.
- **Список**: вкладки — годы, которые есть в данных (`tab=2017`, `2016`). Поиск по ФИО. Сортировка `-tp` (годовой план). Колонки m0..m11 — план/факт в млн; `tp` = Σplan; `pct` = Σfact/Σplan·100. Ответственный — `u`, «Передать» нет. Карточек нет.
- **KPI** (опорный месяц 2017-12; суммы по месяцам периода в пределах года): «План», «Факт (сумма КП)», «Выполнение %» — у всех трёх есть `prev`; «Менеджеров в плане» за год. `series?metric=fact` — факт по месяцам, ₸.
- **Карточка**: вкладка «По месяцам» — таблица месяц / план / факт / %. Действие «Изменить план» открывает форму.
- **Форма**: задуманы менеджер `u` + 12 полей плана (`m0..m11`, ₸) в `fields`. Но в `formOf` колонки месяцев помечены `noSort` и отбрасываются, поэтому сейчас в форме только «Менеджер» и «План, млн» / «Выполнение» (только чтение). Год в форме не выбирается (по умолчанию 2017). Для API: `POST /sales-plan { u, y, plan: number[12] }`, `PATCH /sales-plan/:id { plan }`; пара (u, y) уникальна.
- **Что нужно с API**: факт по менеджеру и месяцу и правило, что считать фактом (сумма КП, подписанные договоры, начисления?) — сейчас считается от КП.

### 18 ИПР — `/ipr`
- **Сущность** `IprRow`: `id`; `u: uid` — менеджер; `cs: number` — клиент; `y: number` — год; `m: number` — месяц 1–12 (0 — на весь год); `sv: string` — услуга (сейчас хранится **название**, на сервере нужен id услуги); `p: number` — ожидаемый объём, ₸; `cm: string` — комментарий.
  Демо `ipr-demo.json`: `rows: [id, u, cs, y, m, svId, p, cm][]`, `services: [id, name][]` (в названиях бывают дубли с пробелом в конце).
- **Список**: вкладки `17` (2017), `16` (2016), `a` — с API лучше вкладки по годам. Фильтр `sv` (услуга). Поиск: менеджер, клиент, услуга, комментарий. Сортировка `-p`. Ответственный — `u`, «Передать» есть. Карточек нет.
- **KPI** (не зависят от переключателя периода): «Объём ИПР 2017» (prev — 2016), «Строк плана» (prev), «Клиентов» и «Менеджеров» — уникальные за год. С API — текущий год против прошлого: `GET /ipr/kpis?year=`.
- **Карточка**: вкладка «Строка». Действие «Изменить» открывает форму.
- **Форма**: менеджер `u`, клиент `cs` (по ID), услуга `sv` (весь справочник услуг), месяц `m` (Весь год / 1–12), объём `p`, комментарий `cm`. Год в форме не задаётся (по умолчанию 2017) — его нужно добавить.
- **Справочники**: `dict/services` (услуги прейскуранта), сотрудники, контрагенты.

### 19 Прогнозы — `/forecasts`
- **Сущность** `Forecast`: `id`; `cs` — клиент; `u: uid` — менеджер КБ; `name` — проект; `blk: "B2B"|"B2G"|"КМГ"|"B2O"` — блок продаж; `cost` — стоимость без НДС, ₸; `mo` — ежемесячная плата, ₸; `prob: 10|25|50|75|90` — вероятность, %; `start: YYYY-MM-DD` — дата начала; `weeks: number` — недель без обновления статуса (сервер считает по дате последнего обновления: `updated_at` → weeks). В карточке есть «Срок реализации, мес.» — сейчас случайный, в сущность нужно добавить поле `term`.
- **Список**: вкладки `a` Все, `h` Вероятность ≥ 75%, `p` Проблемные (weeks > 12). Фильтр `blk`. Поиск: клиент, проект, менеджер. Сортировка `-cost`. Ответственный — `u`, «Передать» есть. Диапазон дат — по `start`.
- **KPI**: «Портфель проектов» = Σcost; «Взвешенный бюджет» = Σ(cost·prob/100); у обоих сейчас условный prev (×0.88, ×0.92) — нужен настоящий срез прошлого периода (снимок портфеля); «Проектов»; «Проблемные зоны» (weeks > 12).
- **Карточка**: вкладка «Проект». Действие «Обновить статус» → `POST /forecasts/:id/status { prob, comment }` → `weeks=0`, вероятность обновляется, в историю пишется запись (сейчас только обнуляется `weeks`).
- **Форма**: проект `name` (обязательно), блок `blk`, менеджер `u`, стоимость `cost`, плата `mo`, вероятность `prob` (при изменении `weeks=0`), начало `start`, «Без обновления» `weeks` (число, редактируется — на сервере поле должно быть вычисляемым). **Клиента `cs` в форме нет** (нет колонки) — новый прогноз создаётся без клиента, поле нужно добавить.
- **Сейчас на фронте**: 90 проектов — пример данных (в копии базы такой таблицы нет).

### 20 Тендеры — `/tenders`
- **Сущность** `Tender`: `id`; `num: string` — номер закупки «№1234567»; `name` — предмет; `org` — заказчик (сейчас строка, лучше ссылка на контрагента); `sp` — способ закупки (Открытый конкурс / Запрос ценовых предложений / Из одного источника / Электронные закупки / Аукцион); `date` — срок решения об участии; `open` — дата вскрытия; `u: uid` — ответственный ДРТП; `lots: number` — число лотов; `budget` — бюджет, ₸; `dec: "yes"|"no"|"none"` — Участвуем / Не участвуем / Решение не принято; `sub: "Подана"|"Не подана"|"—"` — заявка; `tv: boolean` — есть ТВ/ТР; `res: ""|"win"|"lose"` — итог; `ks: "ТК"|"ТО"|"СИ"`.
- **Список**: вкладки `ann` Объявления (dec=none), `w` Не отработанные (dec=yes и sub="—"), `s` Подана заявка, `r` Отказ от участия, `a` Все. Фильтры `sp`, `ks`. Поиск: name, num, org. Сортировка `-date`. Ответственный — `u`, «Передать» есть. Плашка статуса на карточке — `dec`.
- **KPI**: «Объявлений» за период по `date` (prev сейчас условный); «Подано заявок» (prev условный); «Выиграно» и примечание «из N с итогами»; «Бюджет в работе» = Σbudget при dec=yes.
- **Карточка**: вкладки «Тендер»; «Лоты» — сейчас бюджет поровну и случайный город → `GET /tenders/:id/lots` (записи раздела 21, связь по `num`/`tender_id`); «Итоги» — результат, наша цена, цена победителя, причина (сейчас вычисляются из бюджета) → поля `our_price`, `winner_price`, `lose_reason` в тендере или `GET /tenders/:id/result`.
- **Действия**: «Участвуем» → `POST /tenders/:id/decision { dec: "yes" }`; «Не участвуем» → `{ dec: "no" }` (сбрасывает `sub="—"`; стоит добавить причину); «Делегировать» → `assign`. Подачи заявки и ввода итогов нет — нужны `POST /tenders/:id/submit` и `POST /tenders/:id/result { res, our_price, winner_price, reason }`.
- **Форма**: наименование `name` (обязательно), заказчик `org`, срок решения `date`, вскрытие `open`, бюджет `budget`, ответственный `u`, решение `dec` (выбор), ТВ/ТР `tv` (да/нет). `num`, `sp`, `lots`, `ks` в форме нет (нет колонок) — их нужно добавить.
- **Интеграция**: загрузка объявлений с портала госзакупок и автораспределение по менеджерам (так написано в подзаголовке страницы) — серверная задача.

### 21 Лоты — `/lots`
- **Сущность** `Lot`: `id`; `ten: string` — номер закупки (связь с тендером 20; лучше `tender_id`); `name`; `budget` — без НДС, ₸ (с НДС в карточке = ×1.12, ставку лучше отдавать с сервера); `place` — место поставки (город); `guar: 0|1|3` — обеспечение заявки, %; `comp: number` — число конкурентов; `res: "win"|"lose"|"wait"` — Выигран / Проигран / Ожидает итогов. Нужны поля, которых нет: причина отклонения (для lose), `deal_id`.
- **Список**: вкладки `a` Все, `w` Выиграны, `l` Проиграны, `o` Ожидают. Фильтров нет, ответственного нет. Поиск: name, ten, place. Сортировка `-budget`. Плашка статуса на карточке — `res`.
- **KPI**: «Лотов»; «Выиграно» (prev условный); «Доля побед %» = win / (win+lose); «Бюджет выигранных».
- **Карточка**: вкладки «Лот» и «Конкуренты» (сейчас имя и цена = бюджет × 0.82/0.86/…) → `GET /lots/:id/bids` → `[{ competitor, price }]`; при этом `comp` = число bids.
- **Действия**: «Добавить риск» — сейчас кнопка без действия → `POST /lots/:id/risks { text, level }` (новая сущность). «Связать со сделкой» — сейчас просто переход в `/deals` → `POST /lots/:id/link-deal { deal_id }`.
- **Форма**: лот `name` (обязательно), место `place` (выбор из городов), бюджет `budget`, обеспечение `guar` (0/1/3), конкурентов `comp`, итог `res`. Номер закупки `ten` в форме не задаётся — нужно поле выбора тендера.
- **Справочники**: города (`dict/cities`), конкуренты (`dict/competitors`: сейчас «Казахтелеком», «Beeline Business», «Transtelecom», «2Day Telecom»).

### 22 Отчёты по тендерам — `/tender-reports`
- **Сущность** — каталог отчётов: `{ id, n: название, d: описание }`, 4 жёстко заданных отчёта: 1 «Отчёт по тендерам», 2 «Отчёт по лотам», 3 «Полный отчёт по лотам» (лот × конкурент × цена × итог), 4 «Отчёт по конкурентам» (конкурент, участий в лотах, средняя скидка к бюджету %). Сейчас CSV собирается в браузере из записей разделов 20/21.
- **Список**: таблица без карточек, без вкладок и фильтров; «Сформировать» в шапке — для отмеченных отчётов (bulk). CRUD по каталогу не нужен.
- **KPI** (за год против прошлого года; сейчас константы 540/470, 118/101, 37/29, 31%/29%): «Тендеров за год», «Заявок подано», «Побед», «Доля побед %» → `GET /tender-reports/kpis?year=`.
- **Карточка**: вкладка «Параметры» (период, филиал, менеджер, формат — сейчас заглушка).
- **Действия**: «Сформировать» → `GET /tender-reports/:id/run?from=&to=&branch=&u=&format=xlsx` → файл. Для пакета: `POST /tender-reports/run { ids, from, to, branch, u }` → zip или несколько файлов.

### 23 Продукт-каталог — `/catalog`
- **Сущность** `CatalogItem` (позиция **действующей** версии прейскуранта): `id`; `ct: string` — тип абонента (id из `clientTypes`); `sv: string` — группа услуг (сейчас название, нужен id); `pos: string` — номер позиции «5.2» (сортировать по частям числа: «12.3» → 0012.0003); `d` — наименование; `ms` — единица измерения (название); `mon: boolean` — ежемесячный; `traf: boolean` — за трафик (если оба false — единовременный); `price: number` — стоимость, ₸ (судя по договорам и КП, без НДС: в них ×1.12); `disc: number` — максимальная скидка, %.
  Демо `catalog-demo.json`: `price: [id, ct, svId, pos, d, msId, mon"0/1", traf"0/1", price, disc][]`, `units: [id, name, ?][]`, `services: [id, name][]`, `clientTypes: [id, name, hint, ?][]`.
- **Список**: вкладки `m` Ежемесячные, `o` Единовременные, `t` За трафик, `a` Все. Фильтры `ct`, `sv`. Поиск: d, pos, sv. Сортировка `pos` по возрастанию. Ответственного нет. Карточек нет. Параметр версии: `GET /catalog?version=current|<id>`.
- **KPI**: «Позиций в прейскуранте» (+ номер текущей версии в примечании), «Ежемесячных», «Единовременных», «Групп услуг» — всё по текущей версии.
- **Карточка**: вкладка «Позиция». Действие «Добавить в КП» → `/offer-builder?pos=<id>` (Конструктор КП пока не принимает этот параметр). В шапке: «Сформировать КП», «Конструктор прейскуранта».
- **Форма** (своих полей нет, всё по колонкам): позиция `pos` (обязательно), услуга `d`, группа `sv` (выбор), ед. изм. `ms` (текст), стоимость `price`, макс. скидка `disc`. Тип абонента и вид платежа (`mon`/`traf`) в форме не задаются. Вопрос для бэкенда: можно ли править каталог напрямую или только через версию (24)? Сейчас правки каталога в версии не попадают.

### 24 Конструктор прейскуранта — `/price-builder`

### 28 Конструктор КП — `/offer-builder`
Страница-инструмент (не список). Параметры адреса: `?kp=<id>` — правка КП из реестра (05); `?cs=<id>` — новое КП для контрагента; `?pos=<id>` — новое КП с позицией каталога; `?deal=<id>` — привязать к сделке.

Сейчас позиции сохранённого КП не хранятся и восстанавливаются по формуле от № КП.
- **Шапка КП (ввод)**: `cs`, `branch`, `currency: "KZT"|"USD"|"EUR"` (сейчас только переключатель, пересчёта нет — нужны курсы или правило), `date` (Дата КП), `valid_until` (Действует до). Номер КП выдаёт сервер (сейчас — следующий свободный id).
- **Позиция**: `{ item_id (позиция прейскуранта, или null для «Вручную»), pos, name, unit, mon: boolean, price, qty, disc %, max_disc % }`. `max_disc` = `catalog.disc` или 10, если у позиции 0; у ручной строки `max_disc = 0` (любая скидка требует согласования), название редактируется, цена по умолчанию 10 000, `mon=true`. Цену, кол-во и скидку можно править у любой строки. Позиции «за трафик» попадают в единовременные (`mon=false`).
- **Доп. затраты**: `extra: { mat, work, eq }` (₸ — материалы, работы, оборудование), `comment` — комментарий по скидке, `files[]` — вложения (сейчас сохраняются только имена файлов, сами файлы не загружаются) → `POST /offers/:id/files` (multipart).
- **Расчёт** (сейчас на фронте; источником правды должен стать сервер — `POST /offers/calc` с тем же телом → итоги):
  - `lineSum = qty × price × (1 − disc/100)`
  - `monthly = Σ lineSum (mon)`, `once = Σ lineSum (!mon)`, `full = Σ qty × price` (по прейскуранту)
  - `extras = mat + work + eq`, `discount = full − monthly − once`
  - `vat = (monthly + once + extras) × 0.12`, `total = monthly + once + extras + vat` («Ожидаемая стоимость с НДС»)
  - `over` = строки, где `disc > max_disc` → «Нужно согласование скидки»; КП сохраняется с `act = over.length ? 0 : 1` (0 — на согласовании, 1 — согласовано).
- **Шаги** (только UI): Клиент → Позиции → Скидка (в пределах / нужно согласование) → Отправка.
- **Действия**:
  - «Сохранить КП» (нужна хотя бы одна позиция) → `POST /offers` / `PATCH /offers/:id` с телом `{ cs, deal?, branch, currency, date, valid_until, items[], extra, comment }` → `Offer { id, cs, u (= менеджер клиента), deal, date, act, n (= число позиций), s (= round(total)) }`. Сейчас в реестр пишутся только эти итоговые поля, а позиции теряются.
  - «Запрос на скидку» (активна, когда есть `over`; обязателен `comment`) → сохраняет КП, затем `POST /discount-requests { kp_id, comment }` → `Discount { id = № КП, cs, u, date, req = over.length, ok = 0, s = full, es = monthly + once, state: "new" }` → переход на `/discount-requests/:id`. На сервере: уведомить согласующего, хранить по строкам, какая скидка запрошена и какая одобрена.
  - «Печать / PDF» — сейчас простая HTML-страница в новом окне (клиент, таблица позиций, «Итого с НДС») → `GET /offers/:id/pdf` по шаблону КП с подписью из профиля (29).
  - «Сформировать договор» → `/contract-builder?kp=<id>` (30).
  - Из каталога (23) приходит `?pos=` — новое КП с этой позицией.
- **Проверки на сервере**: позиции из действующей версии прейскуранта; цена ручной строки и скидка выше допустимой → статус «на согласовании»; `valid_until ≥ date`.

- **Сущность** `JobOrder`: `id`; `num: string` — «НЗ-3000»; `cs`; `u` — курирующий менеджер; `work: string` — вид работ (13: Подключение, Приостановление, Возобновление, Отключение, Тестовое подключение, Изменение маршрутизации, Изменение IP-адресации, Увеличение, Уменьшение, Перенос, Переоформление, Смена технологии, Отправка оборудования); `type: "Централизованный"|"Локальный"`; `cat: "Стандартный"|"Нестандартный"` (плановый срок 5 / 15 рабочих дней); `so: boolean` — через стороннего оператора; `noc: boolean` — без подписанного договора (нужно согласование ЗДК); `st`; `date` — создан; `trv`, `kpv: number` — версии последних ТР и КП; `ip`, `idc`, `tel: boolean` — есть исполненные заявки IP (11) / ID-канал (40) / номера (12); `br` — филиал; `wo: string` — номер наряда на работы «Н-18000».

- **Список**: вкладки `w` (st ≠ wo) · `wo` · `a`. Фильтры `type`, `work`, `cat`. Поиск: num, контрагент, вид работ. Сорт `-date`. Owner = `u`, `set` есть → «Назначить исполнителя» = assign.
- **KPI**: «Наряд-заказов» за период по date (prev); «Централизованных»; «Нестандартных»; «Ждут согласования» (st=appr).
- **Карточка**: «Наряд-заказ» (баннер noc; параметры, в т. ч. точка подключения); «Документы» — подтянутые последние версии ТР и КП, исполненные заявки IP / ID / номера; блок СО (маршрут согласований пройден, документы ТР/рентабельность приложены); «Маршрут» — шаги по типу: Централизованный — Курирующий менеджер → ОТУП ДИППП (консолидатор ГО) → Главный инженер филиала → Исполнитель работ; Локальный — без ОТУП. `route: { step, uid?, date?, state: done|on|todo }[]`; сроки.
  - `GET /job-orders/prefill?cs=&pointId=` → последние версии ТР, КП и исполненные заявки — **обязательное** подтягивание при создании.
- **Действия**:
  - `POST /job-orders/:id/make-order` «Сформировать наряд»: если st=wo → 409 «уже сформирован»; если noc и нет согласования → 409/переход в appr с запросом ЗДК / директору департамента; иначе создаёт наряд на работы в разделе 10 (связан с наряд-заказом, `wo` = его номер), st → wo, маршрут стартует. На фронте с «Отменить».
  - `POST /job-orders/:id/approve|decline` — согласование ЗДК для noc (нет на фронте).
  - Отметки этапов маршрута `POST /job-orders/:id/route/:step/done` — ждут API.
  - «Назначить исполнителя» → `assign` (меняет `u`).
- **Фон**: если `work = "Отключение"` — при формировании наряда автоматически создать заявку на изменение статуса ID-канала (40, auto) и, видимо, изъятие IP (43 «авто при отключении»). Подключение без договора — «по логике тестового подключения», начисления по последней версии КП.
- **Форма** (свои fields по колонкам): num* «Наряд-заказ» (text; на фронте вручную — лучше генерировать); cs «ID контрагента» (number); type (select); cat (select); docs «ТР · КП · IP · ID · №» (строкой, парсится в trv/kpv/ip/idc/tel — в API заменить выбором ТР/КП/заявок); u (сотрудник); date (date, по умолчанию сегодня); st (select — не принимать). work, so, noc, br, wo — из blank (Подключение, нет, нет, первый филиал, по id) — **вид работ, СО, договор и филиал в форме отсутствуют** (как в макете), нужно добавить.
- **Справочники**: WORKS, BRANCHES, сотрудники, контрагенты, точки, ТР, КП, договоры.
- **Сейчас на фронте**: 130 записей сгенерированы; документы — заглушки; наряд в 10 не появляется; маршрут — схема.
